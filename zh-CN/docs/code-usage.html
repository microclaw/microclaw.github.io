Using MicroClaw Code

This page covers the day-to-day use of mccode: the terminal interface, permission modes and approvals, the shell sandbox, project trust, verification, sessions, scripting and evaluation. Install and first steps are in Overview and install. Modes, approvals, the sandbox, trust, verification and sessions work the same in Zed; the Zed panel itself is described in Use with Zed.

Use​

mccode                                   # full-screen interface
mccode "fix the failing parser test"     # start with a task
mccode -c                                # continue the most recent session here (shows its history)
mccode --session <id>                    # resume a session (see `mccode sessions`)
mccode -p "add a --verbose flag" --mode auto   # one task, then exit
mccode -p "explain the build" --json            # JSON Lines runtime events
microclaw code …                         # same, through the Server binary

In the TUI:

Keys can be rebound, and themes, the status line and the screen mode changed, in settings. Large pastes collapse into a [Pasted #1 +120 lines] chip that is expanded when you send.

Commands: /help, /mode [plan|ask|auto], /plan [task], /check [name|all], /verify [on|off], /trust, /allow, /diff [full], /new, /sessions, /status, /init, /clear, /exit, and:

After a turn that changed files, ran checks or fetched pages, a summary card shows the files and line counts, check results, the sandbox, any network use, tokens and cost, and the checkpoint to rewind to. On wide terminals a side panel keeps the plan, checks, changed files and running sub-agents in view.

Checkpoints are taken at the start of every turn in a shadow git repository inside the Code home (data/checkpoints); they never touch your own .git.

Shell sandbox​

Shell commands (bash, including background processes) run in the operating system's sandbox by default: bubblewrap on Linux and Seatbelt (sandbox-exec) on macOS.

  • They can read the machine, except credential directories (~/.ssh, ~/.gnupg, ~/.aws, ~/.azure, ~/.config/gcloud, ~/.kube, ~/.docker, ~/.netrc, ~/.git-credentials, ~/.microclaw).
  • They can write only the repository, the temp directory and common tool caches (~/.cache, ~/.cargo, ~/.rustup, ~/.npm, ~/.gradle, ~/go, …), so builds and tests keep working.
  • Network access is on; --no-network turns it off. With network off, a command in the sandbox cannot change anything outside the repository, so in ask mode such commands run without asking (destructive ones such as git push or rm -rf still ask).
  • On Linux without a working bwrap, Landlock is used instead: writes are confined the same way (and outgoing TCP is blocked on kernels with Landlock ABI 4+), but credential directories stay readable, so commands keep asking. MCCODE_LOCAL_SANDBOX=bubblewrap|landlock|none overrides the choice.

--review-commands has the model annotate every approval with a one-line verdict; a command it calls DANGEROUS asks you even in auto mode.

This is defence in depth: the approval rules above still apply. Turn it off with --sandbox off (or MCCODE_SANDBOX=off). If the machine has no working OS sandbox (no bwrap, or unprivileged user namespaces disabled), Code says so at startup and commands run unsandboxed; mccode doctor reports the state. The MicroClaw Server can use the same mechanism with sandbox: { mode: all, backend: local }.

Permission modes​

ModeBehaviour
planRead-only tools; the agent proposes a plan. Approve it to switch to ask and execute.
ask (default)File edits apply directly (shown as diffs, with checkpoints); shell commands ask first.
autoShell commands run without asking, except destructive ones (rm -rf, git push, git reset --hard, sudo, curl … | sh, publish, plus your always_ask patterns).

Outside plan mode the agent gets the workspace tool set (ToolPolicy::WorkspaceWrite): file, search, shell, planning, sub-agent and MCP tools, without channel delivery, scheduling, A2A or media tools.

In the TUI an approval pauses the agent in place: the dialog's answer goes back into the same run (approve once, always allow the tool in this session, deny — the agent sees the denial and continues). For shell commands it also offers always allow <command prefix> in this project (key p), for example cargo test. Such a rule covers only single simple commands that start with the prefix (cargo test -p x, but never cargo test && …, pipes, redirections or $(…)); interpreters, sudo, rm, curl and the like cannot be allowed by prefix, and the destructive list above still asks. Rules live in ~/.mccode/allow-rules.json; manage them with /allow [list | add <prefix> | rm <prefix>] or mccode allow [list | add | remove].

In -p mode an approval that needs a person ends the run with exit code 2; resume it with mccode --session <id> -p 1 (approve once) or -p 3 (deny). Exit codes: 0 done, 1 failed / cancelled / checks still failing, 2 approval pending.

Project trust​

.microclaw/project.yaml lives in the repository and can set the mode, add instructions and define check commands, so it only takes effect once you trust the project — for the exact file content you trusted. If the file changes later (for example after a pull), Code asks again. The TUI asks on first use; in -p mode pass --trust; change the decision with mccode trust [--revoke] or /trust. Untrusted projects ignore the file and never run checks automatically (checks execute the repository's own build scripts).

Trusted projects also load the repository's AGENTS.md (or CLAUDE.md, AGENT.md; the first one found, up to 16 KB) into the agent's instructions. In an untrusted project the agent is only told that the file exists.

Verification​

Checks are detected for Rust, Node (npm/pnpm/yarn/bun scripts), Python (ruff/pytest/mypy), Go and Makefiles, or configured in .microclaw/project.yaml. In trusted projects, when a turn changed the working tree — through the file tools or through shell commands — the auto checks run; a failure goes back to the agent (up to max_fix_rounds, default 2) with an explicit instruction not to weaken tests.

mccode info          # detected project, trust, checks, config sources
mccode check         # run all checks
mccode check build   # run one
mccode init          # write .microclaw/project.yaml
mccode doctor        # validate the configuration and start the engine once

.microclaw/project.yaml:

mode: ask
verify: true
max_fix_rounds: 2
checks:
  - name: build
    run: cargo check --all-targets
    auto: true
  - name: test
    run: cargo test
always_ask:
  - terraform apply
instructions: |
  Use pnpm, not npm.
compact_instructions: Keep the names of public APIs and any open TODOs.
lsp: true
max_session_tokens: 3000000
hooks:
  after_edit:
    - cargo fmt

Context and compaction​

The status bar shows how full the model's context window is (ctx 42%; yellow from 70%, red from 85%), and /context breaks it down. Code measures every request against the model's window (known models are recognized by name; set model_context_windows in the model config for others) and, from 80% of it:

  1. clears older tool outputs first (the newest ~40k tokens of output stay; a file read again later replaces the earlier read), then
  2. summarizes older history into fixed sections (goal and constraints, decisions, files and state, errors and fixes, plan, verification, next step), keeping your own earlier messages verbatim and the list of files changed. The last ~24k tokens of the conversation stay as they are.

If summarizing fails, a mechanical digest is kept; history is never dropped silently, and the full conversation is archived before every compaction. A notice in the transcript (and on stderr with -p) says when it happened. /compact <focus> compacts now and tells the summary what matters; compact_instructions in .microclaw/project.yaml does the same for every compaction in the project.

Exploring with helpers​

The agent can hand wide investigations ("where is the retry policy set and who calls it?") to explore, a read-only helper with its own context. Only the helper's short report, with file paths and line numbers, enters the main conversation, and several explore calls run in parallel. Trusted projects can add focused helpers in .microclaw/agents/<name>.md:

---
description: Knows the storage layer and its migrations
model: claude-haiku-4-5   # optional
---
You explain how the database code in crates/storage works. …

The model also sees how full its context is on every request, so it can delegate or wrap up before compaction is needed. With --context-tools (or context_tools: true in the project file) it can additionally save checkpoints (context_note) and rewind its own context to one with a note to itself (rewind_context), dropping failed attempts. Files are not reverted.

Project memory​

In trusted projects the agent keeps durable lessons about the repository in .microclaw/memory.md (how to build and test it, slow tests, pitfalls), edits it with the normal file tools (so you see every change as a diff), and reads it at the start of every session. Edit or delete it like any file.

Custom commands​

A Markdown file defines a slash command; its body is the prompt and $ARGUMENTS is replaced by what follows the command:

---
description: Fix a GitHub issue
---
Fix issue #$ARGUMENTS: read it with `gh issue view`, write a failing test
first, then fix it.

Put personal commands in ~/.mccode/commands/ and project commands in .microclaw/commands/ (trusted projects only; they win on a name clash). /help lists them, Tab completes them, and mccode -p "/fix-issue 42" runs one non-interactively.

Language servers and hooks​

When the agent changed files, MicroClaw Code asks the language server of each file's language for errors before running the checks: rust-analyzer, typescript-language-server, pyright-langserver or gopls, whichever is installed. Errors are handed back like a failed check (lsp), usually faster and more precisely than a full build. Language servers run project code (build scripts), so this needs a trusted project; lsp: false turns it off.

Hooks run shell commands in the project root at fixed points (trusted projects only):

hooks:
  after_edit:            # after the agent changed files, before the checks
    - cargo fmt
  after_turn:            # when a turn that changed files ends
    - ./scripts/notify.sh

A failing hook is reported but does not stop the turn.

Images​

Mention an image file with @ (@docs/screenshot.png, an absolute path or ~/…; PNG, JPEG, GIF or WebP up to 5 MB) and it is sent to the model with the prompt, for example a screenshot of a broken layout or an error dialog. Drag a file into the terminal to paste its path. In Zed, images pasted into the agent panel are attached the same way. The model must support images.

Parallel tasks in worktrees​

mccode -p "add retries to the HTTP client" --mode auto --worktree retries
mccode -p "update the README examples" --mode auto --worktree docs &
mccode worktree list
mccode worktree remove retries

--worktree [name] runs the session in a new git worktree on branch mccode/<name> (under ~/.mccode/worktrees), so several tasks can run at once without touching your checkout or each other. When it ends, Code prints the branch, its commits and how to review, merge or remove it. Trust carries over from the main checkout.

Pull request review​

mccode review --pr 123                 # review the PR's diff, print findings
mccode review --pr 123 "error handling" --post   # …and post them as a PR comment

The diff comes from the GitHub CLI (gh pr diff) or, without it, from origin's refs/pull/123/head. The review runs with read-only tools. --post uses gh pr comment and is the only step that writes to GitHub.

Token budget​

--max-session-tokens 2000000 (or max_session_tokens in the project file) stops a session before the next request once it has used that many tokens (input + output, all models), with a notice; -p exits with status 1.

Windows​

Windows has no OS sandbox for shell commands yet. Commands run with your permissions, ask mode asks before every command, and Code warns when you use auto mode without a sandbox. Prefer ask mode in repositories you do not trust, or use WSL, where the Linux sandbox applies.

Interactive programs​

The agent can drive REPLs and debuggers: it starts one with bash run_in_background, sends input with bash_input and reads output with bash_output. Input goes to stdin without a terminal, so line-oriented modes work best (python3 -u -i, node -i, gdb -q). Background processes are stopped when the session ends.

Scripting and CI​

mccode -p "update the changelog for the new flag" --mode auto --trust
mccode -p "explain the build" --json > events.jsonl
mccode review "error handling" > review.md
  • -p prints the final answer (or, with --json, one runtime event per line) and exits with 0 done, 1 failed / cancelled / checks still failing, 2 approval pending.
  • --trust trusts the project for this run so its checks execute; without it an untrusted project runs no checks.
  • --no-verify skips checks, --no-network turns off network access for shell commands, --sandbox off disables the OS sandbox.

Evaluation​

mccode eval apps/microclaw-code/eval/cases            # PASS/FAIL per case
mccode --json eval my-cases --filter parser            # JSON Lines
mccode eval replay v0.10.0..HEAD --check "cargo test" --out eval/replay

A case is a directory with case.yaml (prompt, check, optional setup, mode, timeout_secs) and a repo/ snapshot. Each case runs in a fresh git repository in auto mode with verification; the case passes when check exits 0 afterwards. eval replay turns bug-fix commits into cases (parent commit = snapshot, commit message = prompt), a regression set built from real history. Results include duration, requests and tokens.
